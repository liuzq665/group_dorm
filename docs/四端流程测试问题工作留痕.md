# 四端流程测试问题工作留痕

## 1. 文档说明

本记录整理《四端流程测试：问题一版》至《问题九版》的测试反馈，用于记录问题来源、需求演变、业务口径和后续验收依据。

版本关系：问题一版首先提出功能缺陷；问题二至七版持续补充业务规则和页面布局要求；问题八版扩展到数据、菜单、备份和四端业务；问题九版集中补充消息来源、人工派单、日期、备份和四端一致性问题。

“未确认”表示原始问题中没有提供修复结果，不能据此判断已经解决。

## 2. 跨版本通用要求

| 编号 | 工作要求 | 来源 | 验收标准 |
|---|---|---|---|
| G-01 | 页面文字不得遮挡 | 二至七版 | 所有四端页面字段完整可读 |
| G-02 | 列间距合理 | 三至七版 | 不重叠、不粘连、不留无意义大空白 |
| G-03 | 禁止横向滚动条 | 二至七版 | 通过列宽、操作区和内容布局解决拥挤 |
| G-04 | 操作按钮不得换行 | 二至七版 | 同一行完整显示操作，操作列标题与按钮左对齐 |
| G-05 | 操作容器统一宽度 | 七版 | 以操作最多的行确定宽度，操作区靠查询列表右侧对齐 |
| G-06 | 修复一个问题不能破坏其他正常功能 | 二、七版 | 回归测试原有功能 |
| G-07 | 数据必须真实且可追溯 | 一、二、八、九版 | 图表和列表数量来自数据库查询，不能编造 |
| G-08 | 多数据场景必须分页 | 四版及后续 | 记录多时分页位置稳定 |

## 3. 按版本记录

### 3.1 问题一版：首次发现的功能问题

**系统管理员**

- 工作台：留宿申请状态、报修工单状态柱状图没有标明统计对象和统计口径，需显示真实数量。
- 消息中心：发布消息的楼栋选择不能取消全选；来源查询会跳回系统通知；查询条件不会保留；消息无法撤回；详情不能显示接收对象；附件预览关闭后无法返回详情。

**宿管**

- 工作台缺少维修评价、住宿、留宿、报修统计图，并且只能查看负责楼栋。
- 消息中心缺少来源筛选，详情中的楼栋为空。
- 报修审核失败，提示服务处理失败。

**维修人员**

- 工作台缺少个人工单记录和个人评价图。
- 消息中心缺少系统通知、系统管理员发布、宿管发布、我发布的来源筛选。

**学生**

- 不需要工作台。
- 消息中心后续需补齐来源筛选和详情能力。

### 3.2 问题二版：明确统计、角色来源和业务规则

- 工作台只修改原有柱状图统计口径和坐标标注，饼图不修改；宿管端按负责楼栋统计。
- 全局禁止操作换行和横向滚动条。
- 宿管消息来源不能照搬管理员端，宿管端不增加“宿管发布”筛选；宿管发布的消息必须在宿管自己的消息中心可见。
- 维修端和学生端的消息来源为系统通知、系统管理员发布、宿管发布；不增加“我发布的”。
- 维修端详情必须显示楼栋。
- 维修工作台个人工单记录支持按年/月筛选，个人评价只显示综合评分和按年/月综合评分。
- 宿管审核通过后不能无条件变成“维修人员负荷已满”；维修人员最大在办工单为不限时，不应触发该结果。
- 维修任务需补齐维修人员实际需要的状态分类，例如待接单。

### 3.3 问题三版：报修、消息和页面交互

**全校报修**

- 待人工原因和派单情况不在列表中显示，派单情况放在详情中。
- 点击“全部”不能自动跳到“待人工处理”。

**消息中心**

- 维修端增加楼栋筛选。
- 时间、阅读状态和操作区不能拥挤或遮挡，四端统一调整。

**维修任务**

- 接单和拒单分开；拒单必须填写原因。

**学生我的报修**

- 确认完成必须填写评分，默认 5 分。
- 固定显示待接单、已接单、待确认等分类，不能因当前没有数据而隐藏分类。
- 重修工单沿用原工单，只增加重修信息，不能创建新的业务工单。

### 3.4 问题四版：状态口径和分页

- “已完成”表示维修人员完成维修但学生尚未确认；“待确认”与该业务含义一致，全校报修和宿管端只保留待确认，确认后的工单进入报修历史。
- 宿管报修审核与派单操作不能被挤出或横向滚动。
- 维修任务必须分页，记录多的所有页面都必须分页。

### 3.5 问题五版：宿管菜单和留宿管理

**宿管工作台**

- 增加负责楼栋空闲床位/已占床位环形图。

**宿管留宿管理**

- “留宿审核”改为一级菜单“留宿管理”，下设全楼留宿、留宿历史。
- 查询项支持学生姓名或学号、专业、锁定状态。
- 批量锁定作用于选中的申请；审核不应被锁定状态限制。
- 人工补录放在申请列表下方。
- 批次发布通知中的申请截止时间必须和实际宿管截止时间一致。
- 去掉统一提交截止。

**宿管报修管理**

- “报修审核与派单”改为一级菜单“报修管理”，下设全楼报修、报修历史。
- 从全楼报修进入报修历史时提供返回按钮；系统管理员端同样提供。

**维修工作台**

- 报修状态板块与消息板块在同一行，消息板块可以较窄，并与下方个人工单记录、个人评价板块对齐。

### 3.6 问题六版：通知发布、锁定和截止时间职责

**系统管理员**

- 全校留宿设置批次时发布消息，接收对象为宿管和学生，提醒开始审核和提交申请。

**宿管**

- 全楼留宿增加“已锁定”查询分类位置要求：最终业务口径修正为“已锁定”属于锁定状态下拉筛选项，不是顶部留宿分类键。
- 审核、锁定/取消锁定操作放在最右侧；提供批量锁定和批量取消锁定。
- 人工补录不受截止时间限制，系统管理员端同理。
- 批次开放区间由系统管理员设置；申请截止时间和自动锁定由宿管设置。
- 宿管发布消息给学生，提醒提交申请截止时间。
- 留宿历史放在申请列表下方。

### 3.7 问题七版：操作区和留宿发布操作

- 操作列标题与每行第一个操作左对齐。
- 操作容器宽度统一，以操作最多的一行为准，并靠查询列表右侧对齐。
- 不得因修复布局破坏原有功能。
- 系统管理员的每个留宿批次不论是否开放，都必须保留“发布消息”操作。
- 宿管必须有设置批次自动锁定时间/申请截止时间的板块，并能发布学生通知。
- 全楼留宿申请列表不能被错误清空；查询项保持留宿批次、学号、姓名、专业等业务字段，锁定状态作为筛选项。

### 3.8 问题八版：数据、菜单、备份和四端业务

**系统管理员**

- 留宿批次上传图片后显示无效。
- “宿舍管理”一级菜单改为“住宿管理”。
- 住宿历史的清空筛选与查询项保持同一行。
- 数据备份任务不能一直处于 waiting，必须能够完成并下载 SQL。

**宿管**

- 截止时间设置板块展示所有开放中的批次，不依赖下方列表当前选择的批次。
- 住宿管理下设宿舍管理、床位管理、住宿历史。
- 增加学生管理一级菜单，并按宿管负责楼栋实现权限范围。

**维修人员**

- 工作台报修数据必须与实际工单一致。
- “维修统计”改为“维修记录”，下设拒单记录、接单超时记录、超时未修好记录、延期记录、重修工单记录。
- 维修历史和维修任务不显示维修人员列；维修任务不显示评分列，历史记录显示已完成评价。

**学生**

- 确认完成时填写评分和文字评价，评价同步到维修、宿管、系统管理员可见的数据。
- 假期留宿增加留宿批次、状态筛选；学生列表隐藏学生、楼栋、重交截止、归档原因等重复字段。
- 报修历史隐藏申请学生列。
- 增加住宿历史，`demo_student_0181` 必须有换宿历史。
- 我的住宿/住宿历史归入住宿管理；我的报修/报修历史归入报修管理。
- 消息来源必须按实际发布人显示，不能逻辑错配。

### 3.9 问题九版：消息、人工派单和数据一致性

**消息中心**

- 无附件时显示“-”。
- 系统通知：发布人为系统。
- 宿管发布：发布人为宿管。
- 系统管理员发布：发布人为系统管理员。
- 来源分类增加“全部”。
- 宿管、维修、学生端点击不同来源后必须返回对应分类数据，不能始终显示未分类列表。

**报修业务**

- “已转人工处理”表示自动派单无法完成，需要宿管或系统管理员人工指定维修人员。
- 维修人员工作台报修数据必须与实际数据一致。
- 维修任务、维修记录和统计概览的数据必须一致。

**系统管理员**

- 留宿批次日期不能出现无效日期。
- 数据备份不能停留在 waiting，必须能完成 SQL 生成和下载。

**宿管**

- 截止时间板块继续展示全部开放批次。
- 消息来源分类必须真正过滤数据。

**维修人员**

- 维修任务不显示维修人员列和评分列。
- 维修历史属于已确认工单，展示历史评价数据。

**学生**

- 确认维修完成时评分和文字评价均为业务数据，并同步到其他端。
- 假期留宿、报修历史、住宿管理、消息来源按问题八的口径实现。

## 4. 合并后的功能验收清单

### 4.1 系统管理员端

- [ ] 工作台柱状图标注统计对象、横纵坐标和真实数量；饼图保持原有功能。
- [ ] 消息来源、阅读状态、楼栋、附件、发布对象、撤回/删除权限正确。
- [ ] 全校报修列表不显示派单情况和评分；详情显示派单情况。
- [ ] 全校报修状态按“全部、待审核、待人工处理、待派单、待接单、维修中、待确认”正确筛选。
- [ ] 报修历史显示评分，不显示归档/关闭原因和重复申请人字段。
- [ ] 全校留宿每个批次始终有发布消息操作。
- [ ] 批次日期、图片/附件、备份任务和 SQL 下载正常。

### 4.2 宿管端

- [ ] 工作台只统计负责楼栋，并有住宿、床位、留宿、报修、评价数据。
- [ ] 消息来源筛选符合宿管角色，不出现不属于宿管的来源。
- [ ] 全楼留宿支持开放批次截止时间/自动锁定、发布学生通知、锁定状态筛选、审核、人工补录、批量锁定/取消锁定、留宿历史。
- [ ] 全楼报修列表不显示评分，工单号和操作区不换行。
- [ ] 报修历史显示评分，不显示归档/关闭原因。
- [ ] 报修审核和人工派单流程正常，不能错误提示负荷已满。
- [ ] 住宿管理和学生管理菜单及权限正常。

### 4.3 维修人员端

- [ ] 工作台统计个人真实工单、超时、延期、重修和评价数据。
- [ ] 维修任务有待接单、维修中、延期、待确认等必要分类，并支持分页。
- [ ] 接单、拒单分开，拒单必须填写原因。
- [ ] 维修任务不显示维修人员和评分；报修历史显示评分，不显示归档/关闭原因。
- [ ] 消息来源、楼栋筛选和详情楼栋显示正确。

### 4.4 学生端

- [ ] 不显示工作台。
- [ ] 我的报修固定显示全部、待审核、待接单、已接单、待确认、待人工处理等分类。
- [ ] 确认完成必须填写评分和文字评价，默认评分为 5 分。
- [ ] 重修沿用原工单，不新建工单。
- [ ] 假期留宿、住宿历史、报修历史和消息来源字段符合学生业务。
- [ ] 消息附件可以预览，来源筛选结果正确。

## 5. 当前工作留痕结论

这九版反馈形成了四条主线：

1. **业务口径线**：状态、人工派单、审核、评价和留宿截止时间职责必须先统一，再做页面展示。
2. **权限线**：四端展示范围不同，宿管按负责楼栋，维修人员按本人任务，学生按本人数据。
3. **数据线**：图表、列表、消息来源、附件和评价必须来自真实数据库关系，不能使用仅用于展示的假数据逻辑。
4. **界面线**：禁止横向滚动和操作换行，列宽、分页、筛选项和操作区需要统一回归测试。

后续每次修改应在本文件对应条目后补充“处理日期、修改文件、验证账号、验证结果”，形成问题闭环。
